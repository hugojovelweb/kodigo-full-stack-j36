1. RESUMEN: QUÉ SE HIZO Y POR QUÉ
=================================

ReservaYa Lab es una práctica de la Semana 20 (Módulo 05) que simula en tu computadora
una arquitectura típica de AWS usando Docker Compose. Con un solo comando se levantan 6
contenedores que trabajan juntos: una puerta de entrada (gateway), un balanceador de
carga, tres réplicas de una API en Node.js y una base de datos PostgreSQL.

El objetivo no es memorizar comandos, sino entender por qué un sistema real se separa en
capas y qué pasa cuando una de ellas falla.

Lo que se practicó:

  - Levantar un sistema de varios servicios con un solo comando (docker compose up -d
    --build).
  - Comprobar el balanceo de carga: las peticiones rotan entre 3 réplicas de la API.
  - Ver el gateway en acción: API key (401), ruta no expuesta (404) y límite de
    peticiones (429).
  - Consultar y modificar la base de datos con psql y probar sus restricciones.
  - Crear un snapshot (respaldo) de la base con pg_dump.
  - Provocar una falla con /api/crash y observar la recuperación automática.



2. LA ARQUITECTURA
==================

    Cliente → gateway (API Gateway) → lb (ALB) → api × 3 (ECS Service) → db (RDS)
               puerto 8080              red interna de Docker (≈ subredes privadas)

Solo el gateway publica un puerto (8080). Todo lo demás vive en la red interna de
Docker, igual que los recursos en subredes privadas de una VPC.

  * gateway
      Archivo: nginx/gateway.conf
      Qué hace: Único punto de entrada. Valida la cabecera x-api-key (401), limita a 5
      peticiones por segundo por IP (429) y devuelve 404 en rutas no expuestas.
      Equivale en AWS: Amazon API Gateway
  * lb
      Archivo: nginx/lb.conf
      Qué hace: Reparte las peticiones entre las réplicas, reintenta con otra si una
      falla y agrega la cabecera X-Atendido-Por.
      Equivale en AWS: Application Load Balancer
  * api × 3
      Archivo: api/index.js, api/Dockerfile
      Qué hace: API Node.js/Express sin estado. Tres réplicas con restart: always.
      Equivale en AWS: Servicio de ECS/Fargate con 3 tareas
  * db
      Archivo: docker-compose.yml, db/init.sql
      Qué hace: PostgreSQL 16 con volumen persistente y sin puerto publicado.
      Equivale en AWS: Amazon RDS for PostgreSQL
  * .env
      Archivo: .env
      Qué hace: Guarda DB_PASSWORD. No se sube a git.
      Equivale en AWS: AWS Secrets Manager


Ideas clave detrás del diseño
-----------------------------

  - Un solo punto de entrada. Todo pasa por el gateway: ahí se concentran la seguridad y
    los límites. La base de datos y las réplicas no son accesibles desde fuera.
  - Réplicas sin estado. La API no guarda nada en memoria: todo vive en la base de
    datos. Por eso se pueden crear, destruir y reiniciar réplicas libremente.
  - Arranque en cadena con healthchecks. db → api ×3 → lb → gateway. Cada eslabón espera
    a que el anterior esté sano, no solo iniciado.
  - Datos separados del código. El volumen db-data conserva la información. db/init.sql
    solo se ejecuta cuando ese volumen está vacío (la primera vez).
  - Secretos fuera del código. La clave de la base viene del archivo .env, que
    .gitignore excluye.



3. ENTORNO Y REQUISITOS
=======================

La práctica se ejecutó en Debian XFCE con Docker Desktop (Docker 29.9.3 y Compose
v5.2.0, contexto desktop-linux). No hace falta instalar Node ni PostgreSQL: corren
dentro de los contenedores.

    docker --version
    docker compose version
    docker info

  NOTA: Si docker info responde sin error, Docker está listo. Docker Desktop corre en
  una máquina virtual con sus propios recursos (en esta práctica: 4 CPUs y unos 2.7 GiB
  de RAM), suficientes para este laboratorio.

Antes de levantar el proyecto, confirma que el puerto 8080 esté libre:

    ss -ltn | grep 8080 || echo "8080 libre"

5. GUÍA PASO A PASO
===================

  NOTA: Todos los comandos se ejecutan desde la carpeta donde está docker-compose.yml.
  Los pasos 1 a 12 corresponden a lo trabajado o pedido en clase; el paso 13 reúne
  complementos del README que conviene practicar. Los IDs de contenedor y de instancia
  que aparecen son de ejemplo: los tuyos serán distintos.


Paso 1. Verificar Docker y el puerto 8080
-----------------------------------------

Qué hacemos: confirmar que Docker funciona y que nada ocupa el puerto 8080.

    docker --version
    docker compose version
    docker info
    docker ps
    ss -ltn | grep 8080 || echo "8080 libre"

Resultado esperado: las versiones de Docker y Compose, docker info sin errores, docker
ps sin ningún contenedor usando el 8080 y el mensaje 8080 libre.

Por qué: si Docker no está corriendo o el puerto está ocupado, el gateway no arranca.

Cuándo usarlo: antes de levantar cualquier proyecto que publique puertos.


Paso 2. Preparar la carpeta del proyecto
----------------------------------------

Qué hacemos: entrar a la carpeta correcta y limpiar basura del zip.

    cd reservaya-lab        # carpeta interna, donde está docker-compose.yml
    rm -rf ../__MACOSX      # basura que deja un zip creado en Mac
    pwd
    ls -la
    cat .env

Resultado esperado: en ls -la aparecen .env, docker-compose.yml, api/, db/ y nginx/. El
.env muestra DB_PASSWORD=cambia-esta-clave.

Por qué: al descomprimir, el proyecto quedó anidado (reservaya-lab/reservaya-lab). Si
estás en la carpeta de afuera, .env y el compose no existen. Además, docker compose
siempre se ejecuta donde está el docker-compose.yml.

Cuándo usarlo: cada vez que recibes un proyecto comprimido. Revisa siempre dónde quedó
el compose y abre en el editor (code .) esa carpeta.


Paso 3. Leer el docker-compose.yml antes de ejecutarlo
------------------------------------------------------

Qué hacemos: entender qué va a crear Docker antes de correrlo. Estas son las líneas
clave:

  * ports: "8080:80" (solo en gateway)
      Qué significa: Es el único servicio accesible desde tu máquina.
  * db sin ports
      Qué significa: La base de datos no es accesible desde fuera.
  * healthcheck
      Qué significa: Cómo sabe Docker si un servicio está sano (pg_isready en la base,
      /health en la API).
  * depends_on con condition: service_healthy
      Qué significa: Espera a que la dependencia esté sana, no solo iniciada.
  * deploy.replicas: 3
      Qué significa: Crea tres copias de la API.
  * restart: always
      Qué significa: Si el proceso se cae, Docker reinicia el contenedor.
  * ${DB_PASSWORD}
      Qué significa: Valor que Compose lee del archivo .env.
  * volumes: db-data
      Qué significa: Los datos sobreviven a docker compose down.

Por qué: un compose de origen desconocido puede publicar puertos o montar carpetas que
no esperas. Leerlo es el primer control de seguridad.

Cuándo usarlo: siempre que levantes un proyecto que no escribiste tú.


Paso 4. Levantar el sistema
---------------------------

    docker compose up -d --build
    docker compose ps
    curl http://localhost:8080/health

Resultado esperado:

  - La primera vez descarga nginx:1.28-alpine y postgres:16-alpine y construye la imagen
    reservaya-lab-api; por eso tarda más.
  - docker compose ps muestra 6 contenedores: db, api-1, api-2, api-3, lb y gateway. La
    base y las tres API aparecen como healthy.
  - Solo gateway muestra 0.0.0.0:8080->80/tcp. db muestra 5432/tcp sin flecha: no está
    publicado.
  - /health responde {"ok":true,"instancia":"4848fd3bd3ea"}.

Por qué: -d deja todo en segundo plano y --build construye la imagen de la API a partir
de su Dockerfile. El orden de arranque lo controlan los healthchecks.

Cuándo usarlo: up -d --build cada vez que cambias código de la API o el Dockerfile. Si
solo cambias configuración de nginx, basta reiniciar el servicio afectado.


Paso 5. Emular 6 peticiones (balanceo de carga)
-----------------------------------------------

Qué hacemos: pedir seis veces la ruta raíz de la API y ver qué réplica responde cada
vez.

    for i in 1 2 3 4 5 6; do
      curl -s -H "x-api-key: kodigo-2026" http://localhost:8080/api/
      echo
    done

Resultado esperado: tres IDs de instancia distintos que se repiten en rotación:

    {"servicio":"reservaya-api","instancia":"9f600a810571"}
    {"servicio":"reservaya-api","instancia":"e9b2edeb1bc8"}
    {"servicio":"reservaya-api","instancia":"4848fd3bd3ea"}
    {"servicio":"reservaya-api","instancia":"9f600a810571"}
    {"servicio":"reservaya-api","instancia":"e9b2edeb1bc8"}
    {"servicio":"reservaya-api","instancia":"4848fd3bd3ea"}

Por qué: curl -s hace la petición en silencio y echo agrega el salto de línea. Que roten
los IDs demuestra que el balanceador reparte la carga entre las réplicas.

Cuándo usarlo: para comprobar que un balanceador realmente reparte, o que una réplica
nueva entró a la rotación.

  ATENCIÓN: Si copias este comando desde un documento con formato, la URL puede quedar
  convertida en enlace (por ejemplo [texto](url)) y curl falla. Escribe la URL en texto
  plano: http://localhost:8080/api/, con el ; después de ella cuando uses una sola
  línea.


Paso 6. Ver IDs y nombres de los contenedores
---------------------------------------------

    docker ps --format "{{.ID}}  {{.Names}}" 

Resultado esperado: una línea por contenedor, con el ID corto y el nombre:

    a1b2c3d4e5f6  reservaya-lab-gateway-1
    b2c3d4e5f6a7  reservaya-lab-lb-1
    4848fd3bd3ea  reservaya-lab-api-3
    e9b2edeb1bc8  reservaya-lab-api-2
    9f600a810571  reservaya-lab-api-1
    c3d4e5f6a7b8  reservaya-lab-db-1

Por qué: el campo instancia que devuelve la API es el hostname del contenedor, que en
Docker es su ID corto. Con esta lista puedes saber qué réplica atendió cada petición.

Variantes útiles:

    # con estado y puertos
    docker ps --format "table {{.ID}}\t{{.Names}}\t{{.Status}}\t{{.Ports}}"

    # incluir contenedores detenidos
    docker ps -a --format "{{.ID}}  {{.Names}}  {{.Status}}"

    # solo las réplicas de la API
    docker ps --filter "name=api" --format "{{.ID}}  {{.Names}}"

Cuándo usarlo: para relacionar lo que dicen los logs o las respuestas con un contenedor
concreto.


Paso 7. Ver las cabeceras del balanceador
-----------------------------------------

    curl -i -H "x-api-key: kodigo-2026" http://localhost:8080/api/

Resultado esperado:

    HTTP/1.1 200 OK
    Server: nginx/1.28.3
    Content-Type: application/json
    X-Atendido-Por: 172.18.0.5:3000
    X-Gateway: reservaya-gateway

    {"servicio":"reservaya-api","instancia":"9f600a810571"}

  - X-Atendido-Por lo agrega el balanceador: es la IP interna y el puerto de la réplica
    que atendió.
  - X-Gateway lo agrega el gateway y prueba que la petición pasó por él.
  - Repite el comando varias veces: la IP y la instancia rotan.

Por qué: -i incluye las cabeceras de la respuesta. Las cabeceras son una forma barata de
dejar rastro de qué componente intervino.

Cuándo usarlo: para depurar por qué una petición se comporta distinto (qué capa
respondió, qué réplica, qué código).


Paso 8. Seguridad del gateway y límite de peticiones
----------------------------------------------------

    # 1. Sin API key: el gateway rechaza
    curl -i http://localhost:8080/api/reservas

    # 2. Ruta que el gateway no expone
    curl -i http://localhost:8080/otra-cosa

    # 3. Rate limit: 20 peticiones seguidas
    for i in $(seq 1 20); do curl -s -o /dev/null -w "%{http_code} " -H "x-api-key: kodigo-2026" http://localhost:8080/api/; done; echo

Resultado esperado:

  - Sin API key: 401 con {"error":"Falta la cabecera x-api-key o no es válida"}.
  - Ruta no expuesta: 404 con {"error":"Ruta no expuesta por el gateway"}.
  - Rate limit: una tanda de 200 seguida de varios 429, con algún 200 suelto entre ellos
    (se recupera cupo a 5 peticiones por segundo). Ejemplo: 200 200 200 200 200 200 200
    429 200 429 429 429 ...

Por qué: el gateway concentra la seguridad: valida la llave, limita el tráfico por IP (5
por segundo con una ráfaga de 5 extra) y solo deja pasar lo que empieza con /api/ (más
/health, que es pública).

Cuándo usarlo: para exponer una API a terceros sin dejar que cualquiera la consuma sin
límite.


Paso 9. Leer y crear reservas por la API
----------------------------------------

    # listar
    curl -H "x-api-key: kodigo-2026" http://localhost:8080/api/reservas

    # crear
    curl -X POST -H "x-api-key: kodigo-2026" -H "Content-Type: application/json" \
      -d '{"cliente":"Lucía Ramos","personas":3,"fecha":"2026-11-22"}' \
      http://localhost:8080/api/reservas

    # listar de nuevo
    curl -H "x-api-key: kodigo-2026" http://localhost:8080/api/reservas

Resultado esperado: al inicio, 2 reservas (Ana López y Carlos Méndez, las de
db/init.sql). El POST responde con la reserva creada (id 3). El último GET muestra 3.

Observación importante: el POST y el GET los atiende normalmente una réplica distinta
cada vez, y aun así todas ven la reserva nueva. Es la prueba de que las réplicas no
guardan estado: todo está en la base.

Validación de la API: si falta un campo, la API responde 400 con {"error":"cliente,
personas y fecha son requeridos"}:

    curl -i -X POST -H "x-api-key: kodigo-2026" -H "Content-Type: application/json" \
      -d '{"cliente":"Sin datos"}' http://localhost:8080/api/reservas

Cuándo usarlo: para probar un endpoint de punta a punta, atravesando todas las capas,
antes de conectarle un frontend.


Paso 10. Entrar a la base de datos con psql
-------------------------------------------

Qué hacemos: como la base no publica puertos, se entra ejecutando psql dentro del
contenedor. Primero se confirma que el 5432 no está expuesto:

    ss -ltn | grep 5432 || echo "5432 no está expuesto"
    docker compose exec db psql -U app_user -d reservaya

El prompt cambia a reservaya=#. Dentro, ejecuta una línea a la vez:

    \dt
    \d reservas
    SELECT * FROM reservas;
    INSERT INTO reservas (cliente, personas, fecha) VALUES ('Hugo Jovel', 2, '2026-11-25');
    SELECT * FROM reservas;
    INSERT INTO reservas (cliente, personas, fecha) VALUES ('Prueba', 0, '2026-11-27');
    \q

Resultado esperado:

  - \dt lista la tabla reservas; \d reservas muestra las columnas y la restricción CHECK
    (personas > 0).
  - El primer INSERT responde INSERT 0 1 y el segundo SELECT muestra tu reserva con id y
    creada_en llenados automáticamente.
  - El INSERT con 0 personas falla a propósito con un error de la restricción
    reservas_personas_check.

  * \dt
      Qué hace: Lista las tablas.
  * \d reservas
      Qué hace: Describe la tabla: columnas, tipos y restricciones.
  * \q (o Ctrl+D)
      Qué hace: Sale de psql. Lleva barra invertida; una q sola no hace nada.
  * \r
      Qué hace: Borra el texto pendiente cuando el prompt quedó como reservaya-#.
  * ; al final
      Qué hace: Toda instrucción SQL (SELECT, INSERT) termina en punto y coma. Los
      comandos con \ no lo llevan.

Verificar desde la API: curl -H "x-api-key: kodigo-2026"
http://localhost:8080/api/reservas debe mostrar Hugo Jovel y no mostrar Prueba.

Dato curioso: el INSERT que falla por el CHECK igual consume un número de la secuencia
SERIAL, así que el siguiente id puede saltarse un valor. Es normal en PostgreSQL.

Por qué: la base tiene su propia validación, independiente de la API. Es la última línea
de defensa de los datos.

Cuándo usarlo: para administrar, auditar o corregir datos sin exponer la base a
internet.


Paso 11. Snapshot de la base de datos
-------------------------------------

Qué hacemos: generar un respaldo lógico (un archivo SQL con la estructura y los datos) y
sacarlo del contenedor.

    docker compose exec db pg_dump -U app_user -d reservaya -f /tmp/snapshot_db.sql
    docker compose cp db:/tmp/snapshot_db.sql ./snapshot_db.sql

  - El primer comando genera el dump dentro del contenedor (-f /tmp/...). No imprime
    nada si todo salió bien.
  - El segundo lo copia a la carpeta de tu proyecto. Sin este paso, el archivo se pierde
    cuando el contenedor se recrea.

Verificar el archivo:

    ls -lh snapshot_db.sql
    grep -A8 "CREATE TABLE" snapshot_db.sql
    grep -A8 "COPY public.reservas" snapshot_db.sql

Debes ver el CREATE TABLE public.reservas y, en el bloque COPY, las filas, incluida la
de Hugo Jovel.

Alternativa en un solo paso (redirigiendo la salida a tu máquina; el -T evita que Docker
meta caracteres de terminal en el archivo):

    docker compose exec -T db pg_dump -U app_user -d reservaya > snapshot_db.sql

Probar que el snapshot sirve (un respaldo sin probar no es respaldo). Se restaura en una
base aparte, sin tocar la real:

    docker compose exec db createdb -U app_user reservaya_test
    docker compose exec -T db psql -U app_user -d reservaya_test < snapshot_db.sql
    docker compose exec db psql -U app_user -d reservaya_test -c "SELECT count(*) FROM reservas;"
    docker compose exec db dropdb -U app_user reservaya_test

El count debe coincidir con el de la base real; el último comando borra la base de
prueba.

  ATENCIÓN: El .gitignore del proyecto solo excluye snapshot.sql. Un archivo llamado
  snapshot_db.sql sí se subiría a git y contiene datos reales. Agrégalo con echo
  "snapshot_db.sql" >> .gitignore y entrégalo por el medio que indique el coach, no por
  el repositorio.

Por qué: un snapshot permite recuperar datos después de un error (por ejemplo, un down
-v), clonar datos a un entorno de pruebas o migrarlos a otra base.

Cuándo usarlo: antes de cambios riesgosos (migraciones, borrados masivos, down -v) y de
forma programada como respaldo.


Paso 12. Botar una instancia de la API (alta disponibilidad)
------------------------------------------------------------

    # 1. Antes
    docker ps --format "{{.ID}}  {{.Names}}  {{.Status}}" --filter "name=api"

    # 2. Botar una réplica
    curl -X POST -H "x-api-key: kodigo-2026" http://localhost:8080/api/crash

    # 3. Justo después: ¿el servicio sigue respondiendo?
    for i in $(seq 1 6); do curl -s -o /dev/null -w "%{http_code} " -H "x-api-key: kodigo-2026" http://localhost:8080/api/reservas; done; echo

    # 4. Después
    sleep 5
    docker ps --format "{{.ID}}  {{.Names}}  {{.Status}}" --filter "name=api"
    docker compose logs --tail=10 api

Resultado esperado:

  - El POST responde {"instancia":"4848fd3bd3ea","mensaje":"Me caigo en 1 segundo"}.
    Anota ese ID: es la réplica que cae.
  - Un segundo después el proceso termina con process.exit(1). En los logs aparece
    Simulando una falla y luego el escuchando en el puerto 3000 de la réplica que
    volvió.
  - El paso 3 debe dar todos 200: el balanceador reintenta con otra réplica y el cliente
    no se entera.
  - En el paso 4, el ID de la réplica no cambia. restart: always reinicia el mismo
    contenedor; lo que cambia es el estado (Up 4 seconds en lugar de varios minutos).

Si alguna petición devolviera 502 o 504, es un buen tema de discusión en clase:
significa que el balanceador no encontró réplica disponible a tiempo.

Por qué: simula lo que hace ECS al reemplazar una tarea caída y lo que hace el ALB al
sacarla de rotación mientras tanto. En el balanceador, max_fails=1 fail_timeout=10s la
aparta 10 segundos y proxy_next_upstream error timeout reintenta la petición con otra
réplica.

Cuándo usarlo: para comprobar que un servicio realmente tolera fallas antes de depender
de él (pruebas de caos a pequeña escala).


Paso 13. Complementos recomendados (del README)
-----------------------------------------------

  NOTA: Estos tres ejercicios no se ejecutaron en la sesión; son la continuación natural
  de la práctica. Los resultados indicados son los esperados según el código del
  proyecto: verifícalos en clase.


>> 13.1 Simular la caída de la base de datos

    docker compose stop db
    curl -i http://localhost:8080/health
    curl -i -H "x-api-key: kodigo-2026" http://localhost:8080/api/reservas
    curl -i -H "x-api-key: kodigo-2026" http://localhost:8080/api/

    docker compose start db
    sleep 10
    curl http://localhost:8080/health

  - /health debe responder 503 con {"ok":false,...,"error":"sin conexión a la base de
    datos"}.
  - /api/reservas debe responder 500 con {"instancia":"...","error":"error interno"}.
  - /api/ sigue respondiendo 200: esa ruta no usa la base.
  - Al arrancar la base de nuevo, el pool de conexiones se recupera y /health vuelve a
    {"ok":true,...}, sin reiniciar las API.

Por qué importa: una réplica con la base caída sigue viva (el proceso no se cae, porque
el pool tiene un manejador de errores). Por eso el balanceador no la saca de rotación y
el síntoma es un 503 o 500, no un 502.


>> 13.2 Escalar las réplicas

    docker compose up -d --scale api=5
    docker compose ps
    for i in $(seq 1 10); do curl -s -H "x-api-key: kodigo-2026" http://localhost:8080/api/; echo; done

    # volver a 3
    docker compose up -d --scale api=3

Deben aparecer 5 IDs distintos rotando. El balanceador consulta el DNS interno cada 5
segundos, por eso ve las réplicas nuevas sin tocar su configuración.


>> 13.3 Limpieza: down contra down -v

    docker compose down        # apaga todo y conserva los datos
    docker compose down -v     # apaga todo y BORRA la base

  ATENCIÓN: down -v borra el volumen db-data: pierdes todas las reservas y, al volver a
  levantar, init.sql vuelve a sembrar solo los 2 datos de ejemplo. Es el equivalente a
  borrar una instancia RDS sin snapshot final. Haz un snapshot (paso 11) antes.



6. CUÁNDO USAR CADA TÉCNICA
===========================

  * docker compose up -d --build
      Úsala cuando: Quieres levantar todo el sistema o aplicar cambios de código en la
      API.
      Ten cuidado si: Solo cambiaste una configuración de nginx: basta reiniciar ese
      servicio.
  * Healthcheck + depends_on: service_healthy
      Úsala cuando: Un servicio no puede arrancar sin otro listo (la API sin la base).
      Ten cuidado si: El healthcheck es demasiado exigente y marca como caído un
      servicio que solo está lento.
  * Réplicas + balanceador
      Úsala cuando: Necesitas más capacidad o seguir funcionando si una instancia cae.
      Ten cuidado si: La app guarda estado en memoria (sesiones, caché local): hay que
      moverlo a la base o a un servicio compartido.
  * Gateway con API key y rate limit
      Úsala cuando: Expones una API a otros equipos o clientes.
      Ten cuidado si: La llave está escrita en un archivo del repositorio. En producción
      va en un gestor de secretos.
  * Base sin puertos publicados
      Úsala cuando: Siempre en producción.
      Ten cuidado si: Necesitas administrarla: usa docker compose exec db psql ....
  * pg_dump (respaldo lógico)
      Úsala cuando: Bases pequeñas o medianas, migraciones, copiar datos a pruebas.
      Ten cuidado si: La base es muy grande: conviene respaldo físico o los snapshots
      automáticos del servicio administrado.
  * restart: always
      Úsala cuando: Un proceso puede caerse y debe revivir solo.
      Ten cuidado si: Hay un error que lo tumba al arrancar: entra en un ciclo de
      reinicios. Revisa los logs.
  * down frente a down -v
      Úsala cuando: down para apagar; down -v solo para empezar de cero a propósito.
      Ten cuidado si: Tienes datos que quieres conservar y no hiciste snapshot.



7. EJEMPLOS HIPOTÉTICOS (TEMAS EXTRA)
=====================================

  NOTA: Estos ejemplos son ideas para practicar y ampliar la clase. No se ejecutaron en
  la sesión: son propuestas basadas en la arquitectura del proyecto.


7.1 Adaptar la arquitectura a otro negocio: «PizzaYa»
-----------------------------------------------------

Escenario: una pizzería quiere recibir pedidos con la misma arquitectura. Se reutilizan
gateway, balanceador y réplicas; solo cambian la tabla y las rutas de la API.

En db/init.sql, una tabla nueva:

    CREATE TABLE IF NOT EXISTS pedidos (
      id         SERIAL PRIMARY KEY,
      cliente    TEXT NOT NULL,
      producto   TEXT NOT NULL,
      cantidad   INT  NOT NULL CHECK (cantidad > 0),
      creado_en  TIMESTAMPTZ NOT NULL DEFAULT now()
    );

En api/index.js, una ruta nueva (el gateway ya reenvía todo lo que empieza con /api/):

    app.get("/pedidos", async (req, res) => {
      const { rows } = await pool.query(
        "SELECT id, cliente, producto, cantidad FROM pedidos ORDER BY id"
      );
      res.json({ instancia: INSTANCIA, total: rows.length, pedidos: rows });
    });

Punto de aprendizaje: init.sql solo se ejecuta con el volumen vacío. Para aplicarlo hay
dos caminos: empezar de cero (docker compose down -v y luego up -d --build, perdiendo
datos) o crear la tabla a mano con psql en la base existente.


7.2 Un día de mucho tráfico (tipo Black Friday)
-----------------------------------------------

Escenario: la API recibe diez veces más peticiones de lo normal.

    docker compose up -d --scale api=8
    docker compose ps

Si los clientes legítimos reciben 429, se sube el límite en nginx/gateway.conf (por
ejemplo rate=20r/s) y se reinicia el gateway:

    docker compose restart gateway

Qué enseña: escalar tiene límites físicos (tu máquina) y un límite de tráfico mal
calibrado rechaza clientes reales. En AWS, el equivalente es el auto scaling del
servicio de ECS según CPU o número de peticiones, y los planes de uso de API Gateway.


7.3 Dos clientes con llaves distintas
-------------------------------------

Escenario: dos empresas consumen la API y quieres poder revocar la llave de una sin
afectar a la otra.

    map $http_x_api_key $api_key_valida {
        default            0;
        "kodigo-2026"      1;
        "cliente-b-2026"   1;
    }

Después de editar el archivo, se recarga la configuración sin apagar el servicio:

    docker compose exec gateway nginx -s reload

Qué enseña: control de acceso por cliente. Escribir llaves en un archivo es solo
didáctico; en producción se usan API keys con planes de uso y un gestor de secretos.


7.4 Respaldo programado con retención
-------------------------------------

Escenario: quieres un respaldo cada noche y conservar solo los últimos 7 días.

    #!/usr/bin/env bash
    set -euo pipefail
    cd /ruta/a/reservaya-lab
    mkdir -p backups
    docker compose exec -T db pg_dump -U app_user -d reservaya > "backups/reservaya_$(date +%F).sql"
    find backups -name "reservaya_*.sql" -mtime +7 -delete

Y en crontab -e, para ejecutarlo todos los días a las 2:00 a. m.:

    0 2 * * * /ruta/a/backup.sh

Qué enseña: un respaldo útil es automático, probado (restaurándolo, como en el paso 11)
y guardado fuera del repositorio y de la misma máquina.


7.5 Guía de diagnóstico de incidentes
-------------------------------------

Escenario: el sistema falla y hay que decidir rápido dónde mirar.

  * 401
      Causa probable: Falta la cabecera x-api-key o es incorrecta.
      Qué comprobar: Revisar la cabecera y el valor del mapa en gateway.conf.
  * 404
      Causa probable: La ruta no empieza con /api/ (ni es /health).
      Qué comprobar: Usar /api/reservas, no /reservas.
  * 429
      Causa probable: Se superó el límite de peticiones por IP.
      Qué comprobar: Esperar, o ajustar rate y burst si es legítimo.
  * 502 / 504
      Causa probable: Ninguna réplica disponible o respondió tarde.
      Qué comprobar: docker compose ps y docker compose logs api.
  * 503 en /health
      Causa probable: La API no llega a la base de datos.
      Qué comprobar: docker compose ps db; si está detenida, docker compose start db.
  * 500 «error interno»
      Causa probable: Falló una consulta (base caída o dato inválido).
      Qué comprobar: docker compose logs api para ver el mensaje real.

Mejora posible: hoy la API acepta personas: -1 (el !personas solo atrapa 0 y vacío) y es
la base la que lo rechaza con un 500. Validar el rango en la API y responder 400 sería
una buena práctica para ampliar la clase.


7.6 Llevar el laboratorio a AWS real
------------------------------------

Escenario: después de entender el modelo local, se quiere desplegar de verdad. La
equivalencia ya está en el diseño:

  * db (Postgres + volumen)
      En AWS: Amazon RDS for PostgreSQL
      Notas: Subred privada, backups automáticos, opción Multi-AZ.
  * api × 3 + Dockerfile
      En AWS: ECS con Fargate (imagen en ECR)
      Notas: El «desired count» reemplaza a replicas; auto scaling opcional.
  * lb (nginx)
      En AWS: Application Load Balancer
      Notas: Health checks y target group en lugar de max_fails.
  * gateway (nginx)
      En AWS: Amazon API Gateway
      Notas: API keys, usage plans y throttling en lugar de limit_req.
  * .env
      En AWS: AWS Secrets Manager
      Notas: Los secretos se inyectan en las tareas, nunca en el repositorio.
  * docker compose logs
      En AWS: Amazon CloudWatch Logs
      Notas: Logs centralizados por servicio.
  * down -v
      En AWS: Borrar RDS sin snapshot final
      Notas: En AWS pide siempre snapshot final.

Qué enseña: lo aprendido en local no es un juguete: cada pieza tiene un servicio
gestionado equivalente, y los conceptos (réplicas, health checks, red privada, secretos)
son los mismos.



8. PROBLEMAS FRECUENTES
=======================

  * cat: .env: No existe el fichero o el directorio
      Causa: Estás en la carpeta de afuera (zip anidado).
      Solución: cd reservaya-lab y ls -la.
  * curl falla con una URL rara como [;](http://...)
      Causa: El comando se copió con formato de enlace.
      Solución: Escribir la URL en texto plano.
  * En psql, q no sale y el prompt queda reservaya-#
      Causa: Faltó la barra invertida o hay texto pendiente.
      Solución: \r para limpiar y \q (o Ctrl+D) para salir.
  * En psql el prompt es -# y no pasa nada
      Causa: Falta el ; al final de la instrucción SQL.
      Solución: Escribir ; y Enter, o \r para cancelar.
  * El puerto 8080 está ocupado
      Causa: Otro programa o contenedor lo usa.
      Solución: docker ps y ss -ltn | grep 8080; o cambiar a "8081:80" en el compose.
  * El snapshot desapareció
      Causa: Quedó en /tmp del contenedor.
      Solución: Copiarlo con docker compose cp (o usar la redirección con -T).
  * 429 en las pruebas
      Causa: Rate limit del gateway.
      Solución: Esperar un segundo y repetir.
  * La primera vez tarda mucho
      Causa: Descarga de imágenes y construcción de la API.
      Solución: Es normal; las siguientes veces usa la caché.

10. GLOSARIO BREVE
==================

  * Contenedor
      Significado: Proceso aislado que corre una aplicación con todo lo que necesita.
  * Imagen
      Significado: Plantilla de la que se crea un contenedor (por ejemplo
      postgres:16-alpine).
  * Réplica
      Significado: Copia idéntica de un servicio, para repartir carga y tolerar fallas.
  * Balanceador de carga
      Significado: Reparte las peticiones entre varias réplicas.
  * API Gateway
      Significado: Puerta de entrada que valida, limita y enruta las peticiones.
  * Healthcheck
      Significado: Comprobación periódica para saber si un servicio está sano.
  * Volumen
      Significado: Almacenamiento que sobrevive a la vida del contenedor.
  * Rate limiting
      Significado: Límite de peticiones por unidad de tiempo (aquí, 5 por segundo por
      IP).
  * Snapshot
      Significado: Copia de la base de datos en un momento dado (aquí, con pg_dump).
  * Servicio sin estado
      Significado: Servicio que no guarda datos en su propia memoria; todo está en la
      base.
